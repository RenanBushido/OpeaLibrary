## Why

The `OpeaLibrary.Application` project (`src/Application/`) implements the CQRS layer (MediatR commands/queries, FluentValidation validators, AutoMapper mappings) on top of the Domain and Infrastructure layers, but it has zero automated test coverage and was never reviewed for correctness. Reviewing it against the Domain/Infrastructure contracts surfaces two real defects: `RequestLoanCommandHandler` and `ReturnLoanCommandHandler` both ignore the `bool` result of `ILoanRepository.RequestLoanAsync`/`ReturnLoanAsync` and unconditionally `return true`, so a failed loan request (book not found, no copies available) or a failed return (loan not found, already returned) is reported to the caller as a success. Separately, `GetBookByIdValidator` exists but is never invoked by `GetBookByIdQueryHandler`, while the three command handlers each manually `new` up and invoke their own validator — duplicated boilerplate that also explains why the query validator was forgotten. Finally, `tests/OpeaLibrary.Infrastructure.Tests` currently fails to compile (12 errors) because `IBookRepository`/`ILoanRepository`'s read methods gained required `CancellationToken` parameters outside of any tracked change, which the Application layer's query handlers already call correctly but the existing Infrastructure tests do not.

## What Changes

- Fix `RequestLoanCommandHandler`/`ReturnLoanCommandHandler` to return the actual `bool` result from `ILoanRepository.RequestLoanAsync`/`ReturnLoanAsync` instead of hardcoding `true`, and to skip `CommitAsync` when the repository call reports failure (nothing was staged to persist).
- Introduce a MediatR `ValidationBehavior<TRequest, TResponse>` pipeline behavior that resolves all registered `IValidator<TRequest>` instances and validates automatically before a handler runs, throwing `FluentValidation.ValidationException` on failure. Remove the manual `new XxxValidator().Validate(...)` calls from `AddBookCommandHandler`, `RequestLoanCommandHandler`, and `ReturnLoanCommandHandler`.
- Wire `GetBookByIdValidator` into the pipeline by registering it with the other validators (it stops being dead code — the pipeline behavior invokes it automatically for `GetBookByIdRequest`, same as every other validated request).
- Add `src/Application/DependencyInjection.cs` (a `IServiceCollection.AddApplication()` extension) registering MediatR handlers, the AutoMapper `MappingProfile`, all `FluentValidation` validators in the assembly, and the `ValidationBehavior` pipeline behavior — there is still no API/Presentation project to call this from, but it is the expected Application-layer deliverable for whenever one exists.
- Rename `ReturnLoanCommnad.cs` to `ReturnLoanCommand.cs` (typo, inconsistent with every other `XxxCommand.cs` file).
- Fix `tests/OpeaLibrary.Infrastructure.Tests` compile errors by passing the now-required `CancellationToken` argument at each `GetBookByIdAsync`/`GetAllBooksAsync`/`GetAllLoansAsync` call site (12 call sites across `BookRepositoryTests.cs`, `LoanRepositoryTests.cs`, `UnitOfWorkTests.cs`) — no behavior change, purely restoring compilability.
- Add a new xUnit test project `OpeaLibrary.Application.Tests` under `tests/`, using **Moq** to fake `IUnitOfWork`/`IBookRepository`/`ILoanRepository`, and a real `MapperConfiguration`-backed `IMapper` (built from the actual `MappingProfile`) for query handler tests, covering:
  - All 3 command handlers (`AddBookCommandHandler`, `RequestLoanCommandHandler` — including the return-value bug fix, `ReturnLoanCommandHandler` — including its fix) and all 3 query handlers (`GetAllBookQueryHandler`, `GetBookByIdQueryHandler`, `GetAllLoansQueryHandler`).
  - All 4 validators (`AddBookValidator`, `GetBookByIdValidator`, `RequestLoanValidator`, `ReturnLoanValidator`).
  - The new `ValidationBehavior` pipeline behavior (valid request passes through to the next delegate; invalid request throws `ValidationException` without calling the next delegate).
  - The `MappingProfile` (`AssertConfigurationIsValid()` plus at least one concrete mapping assertion per map).
- Configure code coverage collection (`coverlet.collector`, matching the other two test projects) targeting 100% line/branch coverage of `src/Application/`.
- **(Added after an `sdd-review` pass, before archive)** `Book.Create` had no way to receive an initial `QuantityAvailable`, and the only path that increments it (`ReturnLoanAsync` → `Book.IncreaseQuantity`) requires an active loan to already exist — meaning a freshly added book could never actually be loaned. Added an optional `quantityAvailable` parameter to `Book.Create` (Domain) with a non-negative guard, plumbed a `QuantityAvailable` field through `AddBookCommand`/`AddBookCommandHandler`/`AddBookValidator`.
- **(Added after `sdd-review`)** `GetBookByIdQueryHandler` silently returned AutoMapper's `null` for a non-existent book despite a non-nullable handler contract. Now throws `KeyNotFoundException` when the book isn't found.
- **(Added after `sdd-review`)** `LoanConfig` had no foreign key from `Loan.BookId` to `Book`, so nothing enforced referential integrity for loans in the real Postgres schema. Added the FK relationship (`DeleteBehavior.Restrict`); confirmed it doesn't conflict with the existing, intentionally-tested orphaned-loan scenario (EF Core's InMemory test provider doesn't enforce FK constraints — only the real Postgres provider will).
- **(Added after `sdd-review`)** Removed the empty, unused `src/Application/Common/Queries/` and `src/Application/Common/Commands/` directories.

## Capabilities

### New Capabilities
- `application-unit-tests`: Automated xUnit test suite validating the Application/CQRS layer (command handlers, query handlers, validators, the validation pipeline behavior, and AutoMapper configuration) against the Domain and Infrastructure contracts, with 100% code coverage as the quality bar.

### Modified Capabilities
- `infrastructure-unit-tests`: `LoanConfig`'s EF Core Configuration Coverage requirement now also covers the `Loan`→`Book` foreign key relationship (see `specs/infrastructure-unit-tests/spec.md` delta, added post-review). The Infrastructure test *compile fix* itself remains a restoration of existing, already-specified behavior — only the FK addition is a genuine requirements change.
- `domain-unit-tests` is unaffected in terms of its spec (the `Book.Create` signature change is additive/backward-compatible — an optional parameter with a default preserving old call sites — and doesn't change any already-specified requirement or scenario).

## Impact

- **Affected code**: `src/Application/Loans/Commands/RequestLoan/RequestLoanCommandHandler.cs`, `ReturnLoan/ReturnLoanCommandHandler.cs` (bug fixes); `AddBookCommandHandler.cs` (validator call replaced by pipeline behavior; now passes `QuantityAvailable` through); `GetBookByIdQueryHandler.cs` (now actually validated, via the pipeline, not directly; now throws `KeyNotFoundException` on a missing book instead of returning `null`); `ReturnLoanCommnad.cs` → renamed; `tests/OpeaLibrary.Infrastructure.Tests/**` (compile fix, 12 call sites, plus a new FK config test); `src/Domain/Entities/Book.cs` (new optional `quantityAvailable` parameter on `Create`); `src/Infrastructure/Persistence/Postgres/Config/LoanConfig.cs` (new FK relationship).
- **New code**: `src/Application/Behaviors/ValidationBehavior.cs`, `src/Application/DependencyInjection.cs`, `tests/OpeaLibrary.Application.Tests/` test project.
- **Removed code**: empty `src/Application/Common/Queries/`, `src/Application/Common/Commands/` directories.
- **New dependency**: `Moq` (test-only, in `OpeaLibrary.Application.Tests`) plus `Microsoft.Extensions.DependencyInjection.Abstractions` (production, in `OpeaLibrary.Application`, for the `IServiceCollection` extension method), plus `Microsoft.Extensions.DependencyInjection`/`Microsoft.Extensions.Logging` (test-only, in `OpeaLibrary.Application.Tests`, to exercise `AddApplication()` end-to-end).
- **Risk**: The `RequestLoanCommandHandler`/`ReturnLoanCommandHandler` fixes and the `ValidationBehavior` introduction are production code changes, not purely additive test scaffolding — flagged explicitly since callers relying on the old "always `true`" behavior would now correctly receive `false` for failed loan operations, and validation now runs even for requests whose handler previously skipped it (`GetBookByIdRequest`). The `Book.Create`/`AddBookCommand` change and the `GetBookByIdQueryHandler` exception change are also production behavior changes, addressed after an `sdd-review` audit surfaced them as gaps left by the original review; both are additive/stricter rather than loosening existing guarantees, and there is still no API/Presentation project consuming any of this, so blast radius today is zero.
