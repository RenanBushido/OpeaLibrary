## Context

`src/` was restructured for CQRS: reads and writes now go through separate repository interfaces and separate storage engines (Postgres for writes via EF Core, MongoDB for reads via `MongoDB.Driver`), wired up by a new `src/CrossCutting` project. `tests/` predates this split and no longer compiles for `OpeaLibrary.Infrastructure.Tests` (17 errors), has zero coverage for the new Mongo read repositories or the new CrossCutting DI extensions, and the two governing OpenSpec capability specs (`application-unit-tests`, `infrastructure-unit-tests`) still describe the old combined-repository, EF-InMemory-only world. This design covers only `tests/` and `openspec/specs/` — no `src/` production code changes.

Two strategy decisions were confirmed with the user before this design was written (see conversation): SQLite in-memory replaces the EF Core InMemory provider for Postgres write-repository tests, and an ephemeral/embedded MongoDB instance is added for Mongo read-repository tests, rather than mocking the driver or skipping coverage.

## Goals / Non-Goals

**Goals:**
- Restore `dotnet test` to a fully green, compiling state across all four test projects.
- Give every persistence implementation introduced by the CQRS split (`BookWriteRepository`, `LoanWriteRepository`, `BookReadRepository`, `LoanReadRepository`) real, non-mocked coverage against the actual technology it targets (relational SQL semantics for Postgres, document semantics for Mongo).
- Give the new `src/CrossCutting` DI composition a test project, closing the coverage gap left by deleting `src/Application/DependencyInjection.cs` and its test.
- Bring `application-unit-tests` and `infrastructure-unit-tests` OpenSpec specs back in sync with the code they govern.

**Non-Goals:**
- No changes to `src/` production code or behavior.
- No changes to `OpeaLibrary.Presentation`/`OpeaLibrary.Api` — it has no test project today and none is added by this change.
- No CI/pipeline wiring changes — this only touches what `dotnet test` covers locally, not how/when it runs.
- Not chasing a specific coverage percentage target for the new Mongo/CrossCutting suites the way the archived `application-unit-tests`/`infrastructure-unit-tests` specs did for their original scope; that threshold question is left to the updated specs to state explicitly rather than assumed here.

## Decisions

### 1. SQLite in-memory replaces EF Core InMemory for Postgres write-repository tests
`TestDbContextFactory.Create()` switches from `UseInMemoryDatabase(Guid.NewGuid().ToString())` to `UseSqlite("DataSource=:memory:")`, opening the `SqliteConnection` before constructing the context and keeping it open for the test's lifetime (an in-memory SQLite database is deleted the moment its connection closes), then calling `Database.EnsureCreated()`. This is Microsoft's own documented recommendation (confirmed via Context7 against the EF Core docs): the InMemory provider is explicitly called out as discouraged for testing because it doesn't enforce relational constraints or translate LINQ the way a real provider does — exactly the kind of gap that let the removed `IBookRepository`/`ILoanRepository` split slip through undetected before. SQLite is a real relational engine, so `BookWriteRepository`/`LoanWriteRepository`'s EF queries execute with genuine SQL translation and constraint enforcement, closer to the production Npgsql provider than the InMemory provider ever was.
- **Alternative considered**: Keep EF Core InMemory, just re-add the missing package reference. Rejected — it was already the wrong tool per Microsoft's guidance even before it broke; re-adding it fixes the compile error but not the underlying test-quality problem the user flagged.
- **Alternative considered**: Drop DbContext-level Infrastructure tests entirely, rely solely on Application-layer Moq coverage of the repository interfaces. Rejected — Moq coverage proves the *handler* calls the interface correctly, not that `BookWriteRepository`/`LoanWriteRepository`'s actual EF/SQL logic (e.g. the `RequestLoanAsync` availability check, the `ReturnLoanAsync` re-return guard) is correct. That logic needs to run against something.

### 2. Ephemeral/embedded MongoDB for read-repository tests, not driver mocking
`BookReadRepository`/`LoanReadRepository` take an `IMongoDatabase` and call `GetCollection<T>(...)`, then chain `Find(...).ToListAsync(...)`/`SingleOrDefaultAsync(...)`. `IMongoCollection<T>`, `IFindFluent<T,T>`, and `IAsyncCursor<T>` are driver-internal types whose real behavior lives largely in extension methods and sealed implementations — Moq can fake the interfaces' method signatures but not reproduce genuine BSON serialization, filter evaluation, or cursor semantics, so a mocked test would mostly prove "the mock returns what I told it to," not that the query is correct. Instead, tests spin up a short-lived, real `mongod` process per test run via an embedded-Mongo test package (e.g. `EphemeralMongo6`), get a real `IMongoClient`/`IMongoDatabase` against it, seed documents directly, and assert `BookReadRepository`/`LoanReadRepository` return the right data — symmetric to the SQLite decision above: both persistence-layer suites become integration-style tests against the real engine's in-memory/ephemeral form, while Application-layer tests remain true Moq-based unit tests against the repository interfaces.
- **Alternative considered**: `Mongo2Go`. Rejected in favor of `EphemeralMongo6`/similar actively-maintained alternatives — `Mongo2Go` has a history of lagging behind current MongoDB server versions and .NET TFMs; the exact package should be pinned during `tasks.md` execution after checking current NuGet availability for `net10.0`.
- **Alternative considered**: A live/shared MongoDB test server (e.g. docker-compose, which already exists in `src/docker-compose.yml`). Rejected for the unit-test suite — it would make `dotnet test` require an external service to be running, which the existing Infrastructure/Application suites explicitly avoid (see the existing `infrastructure-unit-tests` spec's "no external database connection required" scenario); an ephemeral in-process instance preserves that property.
- **Implementation note (`EphemeralMongo6` pinned to `2.0.0`)**: Its actual public API differs from initial expectations — `MongoRunner.Run(MongoRunnerOptions)` is synchronous (no `RunAsync`), confirmed by reflecting over the installed `EphemeralMongo.Core.dll` rather than trusting an initial doc lookup. More significantly, `EphemeralMongo.Core 2.0.0` depends on `MongoDB.Driver 2.28.0`, and its internal graceful-shutdown path (`StartedMongoRunner.TryShutdownQuietly`) references that version's separate `MongoDB.Driver.Core` assembly directly. This solution deliberately unifies on `MongoDB.Driver 3.10.0` (the driver's 3.x line merged `MongoDB.Driver.Core` away entirely), so that assembly can't be found at runtime — `IMongoRunner.Dispose()` throws `FileNotFoundException` during test-collection teardown, after all assertions have already passed. Rather than downgrading the solution's driver version (out of scope — a `src/`-wide production dependency choice) or accepting a nonzero `dotnet test` exit code from a teardown-only quirk, the fixture's `DisposeAsync` catches that specific exception with an explanatory comment; the underlying `mongod` process is still torn down by the runner independent of this failed "ask nicely first" step. No newer `EphemeralMongo6` version was available on NuGet to check for a fix at time of implementation (`2.0.0` was latest).

### 3. New `OpeaLibrary.CrossCutting.Tests` project, structured like the existing three
Mirrors `tests/OpeaLibrary.Infrastructure.Tests`'s shape (xUnit, Moq where needed, `coverlet.collector`, a `GlobalUsings.cs`). Tests build a real `ServiceCollection`, call `AddApiMediatR`/`AddApiAutoMapper`/`AddApiValidators`/`AddInfraPostgres`/`AddInfraMongo`, and assert against `IServiceCollection`'s registered `ServiceDescriptor`s (interface → implementation type, lifetime) rather than always building a full `ServiceProvider` — `AddInfraPostgres`/`AddInfraMongo` read connection strings from `IConfiguration` and eagerly open a real `NpgsqlConnection`/`IMongoClient` in some registrations, so provider-resolution tests use a minimal in-test `IConfiguration` with placeholder connection strings and only resolve the descriptor-level registration, not force a live connection open, keeping the suite free of external dependencies.
- **Implementation note (coverage trade-off)**: Never resolving `IDbConnection`/`IMongoClient` (see above) means their factory delegate *bodies* in `AddInfraPostgres`/`AddInfraMongo` are never executed, so they don't reach 100% coverage. Closing that gap would require either a live, reachable Postgres server (the `IDbConnection` factory hardcodes `NpgsqlConnection` — no swap to a testable substitute without touching `src/`) or importing the ephemeral-Mongo test machinery from `Infrastructure.Tests` into this project too, just to cover a few lines of driver boilerplate already implicitly exercised elsewhere (`Infrastructure.Tests`' Mongo read-repository tests construct a real `MongoClient` against a real connection string directly). Per the same user decision as the `LoanWriteRepository`/`MongoMappings` gaps, this is documented as a spec exception rather than worked around — see `specs/crosscutting-unit-tests/spec.md`'s `100% Code Coverage of CrossCutting Layer` requirement.
- **Implementation note**: `AddApiMediatR`/`AddApiAutoMapper` *do* need to be exercised through a built `ServiceProvider` (to prove `IMediator`/`IMapper` actually resolve and, for AutoMapper, that the configuration is valid) — both of those resolution paths require `ILoggerFactory` to be registered first (MediatR's license-check step, AutoMapper's internal logger), which isn't evident from either extension method's own signature; the corresponding tests call `services.AddLogging()` before invoking the extension. Separately, the initially-assumed `Microsoft.Extensions.Configuration.InMemory` package (for building the placeholder `IConfiguration`) returns no versions on NuGet for this line — `AddInMemoryCollection`/`MemoryConfigurationSource` now ship directly inside the core `Microsoft.Extensions.Configuration` package (confirmed at `10.0.10` by reflecting over the installed assembly), so no extra package reference was needed for that part.

### 4. Test renames follow production renames 1:1
`BookRepositoryTests.cs` → `BookWriteRepositoryTests.cs`, `LoanRepositoryTests.cs` → `LoanWriteRepositoryTests.cs`, `GetAllBookQueryHandlerTests.cs` → `GetAllBooksQueryHandlerTests.cs` (test class names follow suit). No behavior renames beyond matching the already-renamed production types — keeps the mapping from test file to system-under-test obvious for future changes.

### 5. Dropped the orphaned-loan scenario instead of working around the FK
The pre-existing `LoanRepositoryTests.ReturnLoanAsync_WhenAssociatedBookNoLongerExists_StillMarksReturned` test seeded a `Loan` with no associated `Book` directly via the `DbSet`, then verified `ReturnLoanAsync` still succeeded (exercising its defensive `book?.IncreaseQuantity()` null-conditional). Under SQLite in-memory this insert now fails with a real `FOREIGN KEY constraint failed` error, because SQLite (unlike the EF Core InMemory provider) enforces the `Loan.BookId → Book` foreign key (`DeleteBehavior.Restrict`) that a prior change added. That FK means this state was never actually reachable in real Postgres either — the InMemory provider's lack of constraint enforcement was masking a test that exercised an impossible precondition. The test was removed rather than reworked, since there's no way to legitimately construct that precondition anymore; this is treated as validation of the SQLite decision (it surfaces exactly the kind of gap the InMemory provider was hiding), not a regression. `LoanWriteRepository.ReturnLoanAsync`'s null-conditional itself is unchanged `src/` behavior and out of this change's scope.

## Risks / Trade-offs

- **[Risk]** Embedded-Mongo test packages bundle a real `mongod` binary per platform; CI/dev-machine startup adds a few seconds per test run and a new binary download on first restore. → **Mitigation**: Scope the embedded instance to a single shared fixture per test class (xUnit `IClassFixture`/`ICollectionFixture`) instead of spinning up a new `mongod` per test method, keeping the added latency to roughly one instance per test class rather than per test.
- **[Risk]** Some embedded-Mongo packages fetch the platform-specific `mongod` binary from the network on first use rather than bundling it in the NuGet package itself, which would break `dotnet test` in offline or network-restricted CI runners. → **Mitigation**: During task 2.1's package selection, confirm whether the chosen package bundles its binaries in the NuGet package (preferred) or downloads on first run; if only network-fetch variants are available, flag it explicitly rather than silently accepting a CI dependency on outbound network access. **Confirmed**: `EphemeralMongo6 2.0.0`'s `mongod` binaries ship as ordinary per-RID NuGet dependency packages (`EphemeralMongo6.runtime.linux-x64` etc.), restored like any other package reference — no runtime network fetch.
- **[Risk]** SQLite's SQL dialect and constraint behavior differ from Npgsql's in edge cases (e.g. some FK/type nuances), so a SQLite-green test does not guarantee identical behavior against real Postgres. → **Mitigation**: This is an explicit, accepted trade-off already implicit in the user's chosen direction and Microsoft's own guidance — SQLite in-memory is a closer proxy than the InMemory provider, not a perfect one; nothing in this change claims it replaces a real Postgres integration/E2E test tier, which doesn't exist yet for this project.
- **[Risk]** Adding a new NuGet dependency (embedded Mongo package) for a single test project increases restore surface and requires picking a package that supports `net10.0` and the currently-referenced `MongoDB.Driver 3.10.0`. → **Mitigation**: `tasks.md` includes an explicit step to verify the chosen package's current NuGet listing and TFM/driver compatibility before adding the `PackageReference`, rather than assuming a specific version now.

## Migration Plan

Test-only change; no runtime migration. Sequencing for `tasks.md`:
1. Fix `OpeaLibrary.Infrastructure.Tests` compilation (SQLite swap + write-repository renames) first — it's the currently broken project and blocks `dotnet test` for the whole solution.
2. Add Mongo read-repository tests once the project compiles again.
3. Add `OpeaLibrary.CrossCutting.Tests`.
4. Do the Application-layer rename pass (`GetAllBookQueryHandlerTests` → `GetAllBooksQueryHandlerTests`) — independent of the above, low risk, can happen anytime.
5. Update `openspec/specs/application-unit-tests/spec.md` and `openspec/specs/infrastructure-unit-tests/spec.md` deltas to match, plus the new `crosscutting-unit-tests` spec — already drafted as part of this change's `specs/` artifact.

No rollback concerns beyond normal git revert — nothing here is deployed or user-facing.

## Open Questions

- Exact embedded-Mongo package/version to pin (`EphemeralMongo6` vs. alternatives) — deferred to `tasks.md` execution, resolved by checking current NuGet listings for `net10.0` compatibility at implementation time rather than guessing a version here.
- Whether `application-unit-tests`/`infrastructure-unit-tests`/the new `crosscutting-unit-tests` should keep the prior specs' "100% line and branch coverage" bar verbatim for the *new* Mongo/CrossCutting scope, or state a lighter bar — resolved in the specs artifact by carrying the existing 100% bar forward for consistency with the other two suites, since nothing in this change gives a reason to lower it.
- **Resolved during coverage verification (task 5.3)**: two spots in `src/Infrastructure/Persistence/` can't reach 100% coverage without touching `src/` production code, which is out of this change's scope. Per explicit user decision, both are documented as spec exceptions rather than worked around:
  - `LoanWriteRepository.ReturnLoanAsync`'s `book?.IncreaseQuantity()` null-conditional is dead code — the `Loan.BookId → Book` FK (`DeleteBehavior.Restrict`) guarantees the book always exists. **Follow-up suggestion for a separate change**: consider removing the now-unreachable `?.` defensive check in `src/`, which would restore natural 100% coverage; not done here since it's a production-code simplification, not a test-alignment task.
  - `MongoMappings.Configure()` is never invoked anywhere in `src/` (`InfrastructureExtensions.AddInfraMongo` registers the `GuidSerializer` directly, bypassing it entirely) — apparent orphaned/dead code from earlier development, not something worth a synthetic test just to hit a coverage number. **Follow-up suggestion for a separate change**: decide whether to wire it into `AddInfraMongo` (if the class-map behavior it configures is actually needed) or delete it.
