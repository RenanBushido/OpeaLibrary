## Context

The write side (`OpeaLibraryDbContext`/Postgres, via `BookWriteRepository`/`LoanWriteRepository`) and the read side (MongoDB, via `BookReadRepository`/`LoanReadRepository`) are fully independent today — nothing connects them. `MediatR 14.2.0` is already the Application layer's request pipeline (`IRequestHandler`, `ValidationBehavior<,>`), and `AddApiMediatR` currently scans only the `OpeaLibrary.Application` assembly for handlers. No message broker, outbox table, or background worker exists anywhere in this project (confirmed: no such service in `src/docker-compose.yml`). The user explicitly chose an in-process domain-events + MediatR notification approach over an outbox/background-worker approach, given the project's current scale.

## Goals / Non-Goals

**Goals:**
- Every successful write (`AddBookCommandHandler`, `RequestLoanCommandHandler`, `ReturnLoanCommandHandler`) results in the MongoDB read side reflecting that change, without any change to those three command handlers.
- Keep the mechanism idiomatic and EF-Core-documented: raise events on the Domain entities that changed, dispatch them from a `SaveChangesInterceptor`'s post-commit hook (`SavedChangesAsync`) — confirmed via Context7/EF Core docs as the intended extension point for reacting to a successful save, and via Context7/MediatR docs as the standard `INotification`/`IMediator.Publish` shape.
- Keep `Domain` free of infrastructure dependencies — no MediatR reference in `src/Domain`.

**Non-Goals:**
- Guaranteed crash-safe delivery (outbox pattern) — explicitly deferred; this design accepts an in-process, best-effort dispatch.
- Backfilling any pre-existing Postgres data into Mongo — not needed, since (per the prior connectivity-fix change's verification) no data has ever been successfully written before this change existed.
- Changing `IBookReadRepository`/`ILoanReadRepository`'s read-only Application-facing contract — projection writes happen entirely inside Infrastructure, through `IMongoCollection<T>` directly, not through those interfaces.
- Any changes to `AddBookCommandHandler`, `RequestLoanCommandHandler`, `ReturnLoanCommandHandler`, or their existing specs/tests.

## Decisions

### 1. Domain events live in `src/Domain`, framework-agnostic
`Entity` gains a protected `AddDomainEvent(IDomainEvent)` and public `ClearDomainEvents()`/`DomainEvents` (`IReadOnlyCollection<IDomainEvent>`). `IDomainEvent` is a plain marker interface in `OpeaLibrary.Domain.Events`, with no MediatR dependency (`OpeaLibrary.Domain.csproj` gains no new package references). `Book.Create` raises `BookCreatedEvent`; `Book.DecreaseQuantity`/`IncreaseQuantity` both raise `BookQuantityChangedEvent(BookId, QuantityAvailable)` (one event type, reused — the read side only ever needs "here's the new quantity", not why it changed); `Loan.Create` raises `LoanCreatedEvent`; `Loan.MarkAsReturned` raises `LoanReturnedEvent`.
- **Alternative considered**: Have `MediatR.INotification` implemented directly on the domain event classes. Rejected — would force `src/Domain` to reference MediatR, violating Clean Architecture's dependency rule (Domain must not depend on Application/Infrastructure-level frameworks). Instead, Infrastructure wraps each `IDomainEvent` in a generic `DomainEventNotification<TEvent> : INotification` at dispatch time.

### 2. Dispatch via an EF Core `SaveChangesInterceptor`, not manual calls in `UnitOfWork.CommitAsync`
A new `DomainEventsInterceptor : SaveChangesInterceptor` overrides `SavedChangesAsync` (fires only after a successful save, per EF Core's documented event lifecycle: "SavedChanges event fires at the end of a successful save operation"). It calls `context.ChangeTracker.Entries<Entity>()`, collects `entry.Entity.DomainEvents` for every entry with any, clears each entity's events, then publishes each one (wrapped in `DomainEventNotification<TEvent>`) via `IMediator.Publish`. Registered on `OpeaLibraryDbContext` inside `AddInfraPostgres`, using the `AddDbContext<TContext>((serviceProvider, options) => ...)` overload so the interceptor resolves `IMediator` from the same DI scope as the `DbContext` instance itself (avoiding a captive-dependency mismatch between a longer-lived interceptor and scoped `IMediator`).
- **Alternative considered**: Collect and dispatch events manually inside `UnitOfWork.CommitAsync`, right after `SaveChangesAsync`. Rejected — the interceptor approach is EF Core's own documented extension point for "react after a successful save" (confirmed via Context7), keeps `UnitOfWork` unchanged (it doesn't need to know about domain events at all), and automatically covers any future write path without needing every future repository/handler to remember to call a dispatch step.
- **Consequence**: Because `SavedChangesAsync`'s handlers run to completion before `SaveChangesAsync` itself returns (MediatR's default `ForeachAwaitPublisher` awaits every notification handler), the Mongo projection write completes *within* the same `await _unitOfWork.CommitAsync(...)` call the command handler already makes — a `GET` immediately after a successful `POST` in the same process will already see the projected data, without needing to poll or wait for an async worker.

### 3. Projection handlers live in Infrastructure, write via `IMongoCollection<T>` directly — not through `IBookReadRepository`
`IBookReadRepository`/`ILoanReadRepository` are Application-facing, read-only CQRS contracts (`GetBookByIdAsync`, `GetAllBooksAsync`, `GetAllLoansAsync`) — adding write methods to them would blur that boundary for every Application-layer consumer. Instead, `src/Infrastructure/Persistence/Mongodb/EventHandlers/` gets one `INotificationHandler<DomainEventNotification<TEvent>>` per event (`BookCreatedEventHandler`, `BookQuantityChangedEventHandler`, `LoanCreatedEventHandler`, `LoanReturnedEventHandler`), each taking `IMongoDatabase` directly (same DI pattern `BookReadRepository`/`LoanReadRepository` already use) and calling `ReplaceOneAsync(filter, document, upsert: true)` (creates) or `UpdateOneAsync(filter, update)` (field-level changes) against the `books`/`loans` collections.

### 4a. `Book` needs a `Restore` factory, mirroring `Loan.Restore`
Discovered during implementation: `BookCreatedEventHandler` needs to construct a `Book` with the *same* `Id` the write side already generated (from `BookCreatedEvent.BookId`), to upsert the correct Mongo document — but `Book.Create` always assigns a new `Guid.NewGuid()` and has no way to accept a specific `Id`. `Loan` already has exactly this need solved via `Loan.Restore(id, bookId, loanDate, returnDate, status)` (used for rehydrating from persisted state); `Book` never got the equivalent. Added `Book.Restore(id, title, author, publishedYear, quantityAvailable)`, mirroring `Loan.Restore` exactly — no domain event raised (it's reconstruction, not creation), no validation guards re-run. `BookQuantityChangedEventHandler`/`LoanReturnedEventHandler` don't need this (they use `UpdateOneAsync` with `Builders<T>.Update.Set(...)`, which only needs an expression tree for field-name resolution, not a constructed instance) — only `BookCreatedEventHandler` needed it, since `LoanCreatedEventHandler` already had `Loan.Restore` available.

### 4. `AddApiMediatR`'s assembly scan must also cover `OpeaLibrary.Infrastructure`
Today `AddApiMediatR` does `AppDomain.CurrentDomain.Load("OpeaLibrary.Application")` and registers only that assembly with MediatR — correct for `IRequestHandler`s (all in Application), but the new `INotificationHandler`s live in Infrastructure (they need `IMongoDatabase`, which Application must not reference). `AddApiMediatR` (or `AddInfraMongo`, since that's where the Mongo registrations already live) needs a second `cfg.RegisterServicesFromAssembly(typeof(BookCreatedEventHandler).Assembly)` (or equivalent) so MediatR actually discovers these handlers — otherwise `IMediator.Publish` finds zero registered handlers and silently does nothing (`ForeachAwaitPublisher` with an empty handler list is a no-op, not an error), which would look identical to "it's working" until someone checks Mongo. This was the single most important gotcha in this design — flagged explicitly for `tasks.md` to verify with an actual notification-handler-invoked test, not just a "did it compile" check.

## Risks / Trade-offs

- **[Risk]** If a Mongo projection handler throws inside `SavedChangesAsync`, the exception propagates back through `CommitAsync` to the command handler, which surfaces it as a failure to the caller — even though the Postgres write already committed successfully. The caller would see an error for an operation that actually (partially) succeeded, and no automatic retry exists. → **Mitigation**: Each projection handler catches and logs its own exceptions rather than letting them propagate out of `SavedChangesAsync`; the write-side operation always reports success once Postgres commits, and a projection failure only means that specific read model is stale until the next write to the same entity (logged, not silently lost). This is an explicit, accepted trade-off of choosing in-process dispatch over an outbox — documented here rather than silently discovered later.
- **[Risk]** Forgetting to extend the MediatR assembly scan (Decision 4) makes the whole mechanism a silent no-op — no exception, no log, nothing writes to Mongo, and it would be easy to mistake for "the events aren't firing" when actually "the events fire into a void with zero registered handlers." → **Mitigation**: `tasks.md` includes an explicit end-to-end verification step (real write via a running API, confirmed via direct Mongo query) — not just "the project builds" — mirroring how the prior connectivity-fix change caught the original gap in the first place.
- **[Risk]** `BookQuantityChangedEvent` fires on both `RequestLoanAsync` (decrease) and `ReturnLoanAsync` (increase) — if a future change adds more `Book` mutation methods without remembering to raise this event, that mutation silently won't propagate to Mongo. → **Mitigation**: Accepted as an inherent property of the domain-events-per-mutation approach; not solved by an automated safeguard in this change (would require e.g. reflection-based enforcement, out of scope for this fix).

## Migration Plan

1. Domain layer first (`Entity`, `IDomainEvent`, the four event records, `Book`/`Loan` raising them) — no dependents yet, fully additive, verifiable via `Domain.Tests` alone.
2. Infrastructure: `DomainEventsInterceptor`, wired into `AddInfraPostgres`; the four Mongo projection notification handlers.
3. CrossCutting: extend `AddApiMediatR`'s (or `AddInfraMongo`'s) assembly scan to include Infrastructure's handler assembly.
4. End-to-end verification against `docker compose up` + a running API: repeat the exact `POST /api/books` → `GET /api/books/{id}` round trip that surfaced this gap in the prior change, confirming it now succeeds; also verify `RequestLoan`/`ReturnLoan` update the projected `Book.QuantityAvailable` and `Loan` documents correctly.

No rollback concerns beyond normal git revert — this is additive; no schema/collection shape changes, no data migration.
